# NimbusKV v3.0.0 — Documentation

> **This documents v3.0.0 specifically.** For the current release, see [`v3.0.1`](v3.0.1.md). If you're installing fresh, install the latest version — this page exists for historical reference and for anyone pinned to `nimbuskv==3.0.0`.

> ⚠️ **Known issue in this version, fixed in v3.0.1:** `atomic()` did not notify `subscribe()`/`wait_for()` listeners. The value itself updated correctly, but anything reactive built on top of an `atomic()` change would never fire. If you use `atomic()` together with `subscribe()` or `wait_for()`, upgrade to v3.0.1. See [the v3.0.1 changelog entry](v3.0.1.md#changes-from-v300) for details.

---

## 1. What NimbusKV is

NimbusKV is a reactive, TTL-aware, optimistic-concurrency key/value store for Python. v3.0.0 is a from-scratch architecture, not an incremental update of anything before it:

- **Reads never block, ever.** State lives as an immutable persistent snapshot. A read is just "look at the current snapshot" — no lock, no wait, regardless of what any writer is doing concurrently.
- **Writes don't lock either.** A writer builds a new snapshot and attempts to atomically swap it in. If another writer got there first, it retries against the fresh snapshot instead of blocking. This is an optimistic-concurrency / software-transactional-memory-style design, not a dict behind a mutex.
- **One code path, two runtimes.** The same code runs correctly on standard (GIL) Python and adapts automatically to free-threaded Python (3.13t/3.14t), where the lock-free design gives real parallel throughput instead of GIL-serialized execution. Detection happens once, at import time — no flag to set.
- **Reactive.** `subscribe()` pushes every change to you as it happens.
- **TTL built in.** Keys can expire automatically, firing their own `'expire'` event distinct from a manual delete.
- **Optional persistence.** Memory (default), SQLite, or Redis, as a write-through mirror — the backend is never on the read path; memory is always the live source of truth.

## 2. Install

```bash
pip install nimbuskv
pip install "nimbuskv[redis]"   # only if you want the Redis backend
```

Requires Python 3.9+. The lock-free write path activates automatically on free-threaded builds (3.13t/3.14t); on standard Python everything is still correct, just without the extra write-side parallelism.

## 3. Quick start

```python
from nimbuskv import NimbusKV

ld = NimbusKV()          # in-memory, default
ld.set('foo', 123)
print(ld.get('foo'))     # 123
ld.stop()                # stops the background TTL scheduler thread
```

Or as a context manager, so cleanup happens automatically even on exception:

```python
with NimbusKV() as ld:
    ld.set('foo', 123)
    print(ld.get('foo'))
```

## 4. Core API

### `NimbusKV(backend="memory")`

Constructs a store. `backend` accepts:

| Value | Meaning |
|---|---|
| `"memory"` (default) | No persistence — nothing survives a restart. |
| `"sqlite:/path/to/file.db"` | SQLite-backed, file created if missing. |
| `"redis://host:port/db"` | Redis-backed. Requires `pip install "nimbuskv[redis]"`. |
| A `PersistenceBackend` instance | For custom backends or pre-configured clients (e.g. a `fakeredis` client for testing). |

If the backend already has data, it's loaded into memory before the constructor returns (already-expired keys are skipped).

### `set(key, value, ttl=None)`

```python
ld.set('foo', 123)
ld.set('session:abc', {'user': 'alvin'}, ttl=3600)  # expires in 1 hour
```

Setting a key with no `ttl` cancels any previously pending expiry on that key.

### `get(key, default=None)`

```python
ld.get('foo')            # 123
ld.get('missing', 'n/a') # 'n/a'
```

Always reads from memory — never touches the persistence backend, so this is fast regardless of which backend is configured.

### `delete(key) -> bool`

```python
ld.delete('foo')   # True if it existed, False if already gone
```

Also cancels any pending TTL for that key, so a manual delete can't race with a later automatic expiry.

### `exists(key) -> bool`, `key in ld`

```python
ld.exists('foo')
'foo' in ld
```

### `keys()`, `items()`, `len(ld)`, iteration

```python
ld.keys()     # point-in-time list of keys
ld.items()    # point-in-time list of (key, value) pairs
len(ld)
for k in ld: ...
```

These are snapshot-safe: the list you get back won't change under you even if writers are actively modifying the store while you iterate.

## 5. TTL

```python
ld.set('temp', 'value', ttl=5)  # expires in 5 seconds
```

Expiry fires its own `'expire'` event on `subscribe()`, distinct from `'delete'`:

```python
def on_change(key, event, old, new):
    print(key, event, old, '->', new)

ld.subscribe(on_change)
ld.set('temp', 1, ttl=1)
# ... after 1 second ...
# temp expire 1 -> None
```

Re-setting a key's TTL before it fires correctly replaces the old deadline — the earlier schedule is invalidated, not left to fire alongside the new one.

## 6. Reactive subscriptions

```python
def on_change(key, event, old_value, new_value):
    print(f'{key}: {event} {old_value!r} -> {new_value!r}')

sub = ld.subscribe(on_change)                  # every key
sub_foo = ld.subscribe(on_change, key='foo')   # just 'foo'

ld.set('foo', 1)     # foo: set None -> 1
ld.delete('foo')     # foo: delete 1 -> None

sub.cancel()  # stop receiving notifications
```

`event` is one of `'set'`, `'delete'`, `'expire'`. Callbacks run **synchronously**, in the thread that made the change, immediately after that write succeeds — keep them fast, since a slow callback delays that `set()`/`delete()` call from returning.

> ⚠️ In v3.0.0, changes made via `atomic()` do **not** trigger `subscribe()` callbacks — this is the known bug described at the top of this page.

## 7. Atomic compound updates

```python
ld.set('counter', 0)
ld.atomic('counter', lambda v: v + 1)   # -> 1, safe under concurrent writers
```

`atomic()` replaces manual locking: instead of holding a lock while reading-modifying-writing a key, it applies your function via the retry-on-conflict path — no lock is ever held while your function runs. Your function must be **pure** (no side effects), since it may run more than once under contention.

```python
import threading

ld.set('counter', 0)

def worker():
    for _ in range(1000):
        ld.atomic('counter', lambda v: v + 1)

threads = [threading.Thread(target=worker) for _ in range(10)]
[t.start() for t in threads]
[t.join() for t in threads]

print(ld.get('counter'))  # 10000, exactly — no lost updates
```

## 8. Batch operations

```python
ld.mset({'a': 1, 'b': 2})        # one atomic swap for both keys
ld.mget(['a', 'b', 'missing'])   # {'a': 1, 'b': 2, 'missing': None}
```

`mset()` matters beyond convenience: setting several related keys in one swap means readers never observe a partially-applied update (some keys changed, others not yet). A loop of individual `set()` calls doesn't give you that guarantee.

```python
ld.mset({'account_a': 90, 'account_b': 110})  # both change together, atomically
```

## 9. `wait_for` — thread coordination without polling

```python
import threading

def consumer():
    result = ld.wait_for('job:status', lambda v: v == 'done', timeout=30)
    print('unblocked with:', result)

threading.Thread(target=consumer).start()
# ... elsewhere, another thread ...
ld.set('job:status', 'done')  # consumer's wait_for() returns right here
```

Blocks the calling thread until `predicate(current_value)` is true, driven by the subscription system — not a sleep-and-poll loop. Raises `TimeoutError` if `timeout` elapses first.

## 10. Async

```python
import asyncio
from nimbuskv import NimbusKV

async def main():
    ld = NimbusKV()
    await ld.aset('bar', 'hello')
    print(await ld.aget('bar'))
    ld.stop()

asyncio.run(main())
```

For the default in-memory backend, `aget`/`aset`/`adelete`/`aexists` are **genuinely non-blocking** — no thread spawned, because there's no real I/O to hide behind an executor. When a real backend (SQLite/Redis) is attached, *only* the persistence write is delegated to a thread-pool executor; the in-memory part of every operation still never blocks.

## 11. Persistence backends

```python
ld = NimbusKV(backend='sqlite:/path/to/store.db')
ld = NimbusKV(backend='redis://localhost:6379/0')
```

State is rehydrated from the backend on startup automatically; already-expired keys are skipped during rehydration. A backend is a **write-through mirror only** — it never sits on the read path. If you need a custom backend, subclass `PersistenceBackend`:

```python
from nimbuskv.modules.persistence import PersistenceBackend

class MyBackend(PersistenceBackend):
    def load_all(self):
        return []  # [(key, value, expire_at_or_None), ...]
    def persist_set(self, key, value, expire_at):
        ...
    def persist_delete(self, key):
        ...

ld = NimbusKV(backend=MyBackend())
```

## 12. Architecture

```
NimbusKV (public API)
 ├─ ReactiveStore     in-memory, immutable-snapshot, optimistic-concurrency core
 │                     — readers: lock-free, always
 │                     — writers: build new snapshot, atomic swap, retry on conflict
 │                     — adapts to LOCK_FREE_MODE (free-threaded vs GIL, detected once)
 ├─ ExpiryScheduler    background thread, min-heap, fires TTL expiry against the store
 └─ PersistenceBackend write-through mirror + startup rehydration
                        (NullBackend / SQLiteBackend / RedisBackend)
```

**Why not "true" lock-free CAS?** Python (free-threaded or not) doesn't expose a language-level atomic compare-and-swap to pure-Python code. What CPython does guarantee is that a single reference write isn't torn — readers always see either the fully-old or fully-new snapshot, never a half-written one. Readers exploit that directly (no lock, ever). Writers still need to detect "did I win the race", so the compare-and-swap step itself is guarded by a lock held only for that single comparison+assignment — nanoseconds, not the whole operation. This is the same pattern software-transactional-memory systems use in languages without native atomics.

## 13. What's explicitly not in this version

- **Sandboxed callback execution.** An earlier, pre-3.0 version of this library had a "sandbox" for callbacks; it was actually just a timeout wrapper, not real isolation, and calling it a sandbox was misleading. It was dropped rather than kept under a false name. Real isolation (subprocess/WASM-based) is a planned future addition, not part of v3.0.0.
- **Manual locking (`lock()`/`unlock()`).** Doesn't fit an optimistic-concurrency design — `atomic()` is the replacement.
